## Investigation: is this the new `/`, `mod`, `rem` support?

No, for three independent reasons:

1. **The affected buckets are wrong for that explanation.** A new SMT
   capability can only move obligations *into* `Proved_Safe` from
   `Unproved`/`Unsupported` (more proofs succeeding), or in principle
   `Unproved` if a genuine refutation is now trusted. It cannot make
   already-registered obligations disappear, and it cannot explain
   `Unproved` staying at exactly 8 while `Proved_Safe` and `Unsupported`
   both drop.
2. **The `FP-040` `Property_Error` fallback fires on the identical 21 of
   49 files as the 2026-08-04 baseline** (file list independently
   re-derived from `adalang-verify.stderr` and compared name-for-name) —
   not a wider gap than before, so the new code isn't newly throwing
   inside more files.
3. **`Divisor_Provably_Nonzero` and the new `Integer_Term` case arm are
   both wrapped by `Integer_Term`'s own outer `exception when others =>
   Context.Supported := False;`** (`vc_prover.adb`), so even a hypothetical
   exception from the new code would degrade one obligation to
   `Unsupported`, not remove it from registration — and zero obligations in
   this run used `method: "external-prover"` at all (confirmed via
   `adalang-verify.json`), meaning `VC.Decide` was never reaching a
   `Proved`/`Refuted` verdict here in the first place, old or new.

## Most plausible explanation

The 2026-08-04 baseline's own environment note says its 680/16 numbers came
from `FP-040`'s fix "landed in this same session (**uncommitted at the time
of this run**)" — i.e. a work-in-progress version of that fix, not
necessarily byte-identical to what was actually committed afterward.
Separately, `FP-029` (self-locating an Alire-cached `gnatls` when `PATH`
lacks one) was fixed in this repository after that baseline was recorded
(commit `787ecfd`, in this session's own `git log`), which changes exactly
the kind of GNAT-toolchain-version-dependent name resolution `FP-040`
itself is about (`Call_Expr.P_Kind` failing to resolve a cross-project
call). Both are plausible, toolchain/interim-fix-driven explanations for
why 24 specific obligations inside the same already-`FP-040`-affected files
now go unregistered instead of registered-but-`Proved_Safe`/`Unsupported` —
consistent with the same class of drift `RESULTS` files for `sparknacl` and
`aws` document for this exact session (both traced there to interim fixes,
not to `FP-047`). Unlike those two, this one was not traced to an exact
line-for-line cause: the original 2026-08-04 run's raw JSON was not
archived (`benchmark-results/` is gitignored), so there is no old
obligation list left to diff against the new one. Flagged honestly rather
than guessed.

## Bottom line

The numbers that actually matter for trusting `--verify`'s output —
possible unsoundness and false positives — remain exactly 0, matching
every prior run of this benchmark. `FP-047` (the `/`/`mod`/`rem` SMT work)
is not implicated in the `Proved_Safe`/`Unsupported` drop documented above;
that drop pre-dates this session's own change and traces to the same class
of interim-fix drift already confirmed for `sparknacl` and `aws`. As
`RESULTS_2026-08-04.md` already cautioned, CubedOS's `FP-040` limitation
means its `--verify` obligation count here should still be read as "what
limited signal is available at this revision," not a coverage measurement
— doubly so now that the exact signal has shrunk again for reasons this
run did not fully pin down.
