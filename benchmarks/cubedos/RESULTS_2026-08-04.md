# CubedOS comparison results — 2026-08-04

## Environment and scope

- cubesatlab/cubedos: `c402301000a5a92237e0f7ab106186a48273cf24`
- AdaLang Analyzer: `1.0.0-rc1`, commit `ddb208cacd2935f3b3307eb6897d904e5cc2f7a2`
  plus the `FP-040` fix landed in this same session (uncommitted at the time
  of this run; see `quality/known_analysis_issues.tsv`)
- GNATprove: FSF 16.1.0, Why3 1.8.2+git, CVC5 1.3.2, Z3 4.15.4, Alt-Ergo 2.6.1
- Compiler: Alire `gnat_native` toolchain (this repository's own pin)
- AUnit: Alire `aunit` 26.0.0, resolved via a throwaway crate (see
  `benchmarks/cubedos/README.md`)
- Host: Apple Silicon, macOS 26.5
- Project: `src/cubedos.gpr`, unmodified, 49 files analyzed by both tools
  (the `check/` AUnit test suite and `modules`/`library` core, excluding
  `samples/`, `bench/`, `mercury/`, `scriptbuilder/`, which have their own,
  separate project files not analyzed here)
- GNATprove ran with `--mode=prove --level=4 --prover=z3,cvc5,altergo
  --timeout=60`, explicitly chosen to match SPARKNaCl's own tuned
  configuration; `cubedos.gpr` itself declares an empty `package Prove`

**Unlike SPARKNaCl, CubedOS is not a fully-proved corpus.** GNATprove's own
`--mode=prove` run on unmodified `cubedos.gpr` reports real `high`/`medium`
findings: tasking data races on `Message_Manager.Mailboxes` shared across
`log_server`/`time_server`/`interpreter`/`transport_udp` message loops, a
`Global` aspect omission (SPARK RM 6.1.4(15)), four `out` parameters not
initialized on every path, and a number of `medium` range/precondition
checks where "provers reached time limit before completing the proof". None
of this is a defect in AdaLang; it means GNATprove's own verdict here is not
a trustworthy "ground truth" oracle the way it is on SPARKNaCl, so this
benchmark cannot ask the same "does AdaLang ever disagree with a fully-proved
oracle" question. Its value is a second, structurally different real SPARK
corpus to exercise `--verify` against.

## Confirmed AdaLang precision problem: FP-040

The first real run (before the fix below) reported `--verify` completing
with only 44 proof obligations project-wide, and 21 of the 49 analyzed files
individually logged as `Error processing FILE: ...` — a whole-file abort, not
a per-obligation gap. Both a minimal, AUnit-free, two-project reproduction
and a symbolic backtrace against the real corpus (temporary
`GNAT.Traceback.Symbolic` instrumentation, reverted) traced this to
`Verify_Subprogram`'s `Finalize_Node` (`flow_interp.adb`) calling several
Libadalang properties (`Call_Expr.P_Kind`, `Expr.P_Expression_Type`,
`Base_Type_Decl.P_Designated_Type_Decl`) directly, outside any
`begin`/`exception` block, whenever a node's own per-kind branch needed one.
Libadalang's own `Call_Expr.P_Kind` genuinely fails with `Property_Error`
("undetermined CallExpr kind") for a call whose callee is declared in a
separate, `with`'d GNAT project — confirmed independent of return type,
library-vs-plain project, and generics; this is an upstream Libadalang
precise-resolution limitation, the same category as the already-documented
`FP-029`, not an AdaLang logic error. What was fixable, and is what closes
this entry, is that the failure escaped `Finalize_Node` entirely instead of
being contained to the one affected node: `cubedos.gpr`'s `src/check/`
subtree calls into a separately `with`'d `aunit.gpr` throughout, and the
`modules`/`library` core assigns call results across several branches that
each called a risky property unguarded.

Root cause and fix are recorded in full as `FP-040` in
`quality/known_analysis_issues.tsv`: the second `Call.P_Kind` check now
evaluates into a local flag inside its own `begin`/`exception` block instead
of raising straight out of an `if`-condition, and the entire per-node
dispatch chain in `Finalize_Node` is now wrapped in one outer
`begin`/`exception`, so any branch's own property access failing skips only
that node's own obligations and still falls through to keep walking the
rest of the file. Regression: `tests/verification_cross_project/`, a
two-project fixture run by `run_verification.sh` with an explicit `-P` (the
only fixture in that file that needs one, since the bug only manifests
across a real project boundary).

Effect on this same CubedOS run, before vs. after the fix:

| | Before | After |
| --- | ---: | ---: |
| Files aborted (`Error processing`) | 21 of 49 | 0 |
| Proof obligations | 44 | 680 |
| `Proved_Safe` | 2 | 16 |
| `Definite_Error` | 0 | 0 |
| `Unproved` | 9 | 8 |
| `Unreachable` | 0 | 73 |
| `Unsupported` | 33 | 583 |

All numbers below are from the **after** run.

## Agreement: matched obligations

Matched by `(file, line, check kind)` — see `benchmarks/cubedos/README.md`
and `benchmarks/sparknacl/README.md` for the matching design. **7**
obligations matched 1:1 (up from 2 before the FP-040 fix, since the fix
means AdaLang now actually registers obligations in files GNATprove also has
something to say about), all in bucket 5 ("both flag a problem" — AdaLang
`Unproved`/`Unsupported`/`Unreachable`, GNATprove not-proved on a range or
overflow check).

| Bucket | Count | Meaning |
| --- | ---: | --- |
| Both safe | 0 | AdaLang `Proved_Safe`, GNATprove proved |
| AdaLang conservative | 0 | AdaLang `Unproved`/`Unsupported`, GNATprove proved |
| Possible AdaLang unsoundness | 0 | AdaLang `Proved_Safe`, GNATprove NOT proved |
| AdaLang false positive | 0 | AdaLang `Definite_Error`, GNATprove proved |
| Both flag a problem | 7 | Both non-safe |

As with SPARKNaCl, zero obligations fell in either headline-risk bucket
(possible unsoundness, false positive). With only 7 matched pairs, this is
still a much weaker signal than SPARKNaCl's 886-pair comparison and should
not be read as evidence of anything beyond "no disagreement was observed in
the small sample that survived matching" — most of AdaLang's 680 obligations
still have no GNATprove `--mode=prove` counterpart at their exact location
(see below), the expected shape given `--verify`'s narrower scalar subset.

Coverage-only counts (not compared, not errors):

- 643 AdaLang obligations have no GNATprove `--mode=prove` counterpart for
  that kind at their location: `range-check` (409), `initialization-check`
  (86, a flow-analysis result outside `--mode=prove`'s output, same as
  SPARKNaCl), `integer-overflow` (142), `assertion` (2),
  `loop-invariant-preservation` (2), `loop-invariant-initialization` (2).
- 12 GNATprove checks (of mapped kinds) have no AdaLang obligation at the
  same location: `range-check` (8), `precondition` (4) — plausibly cases
  `--verify`'s narrower relational/precondition handling does not attempt at
  all, though this was not individually confirmed per location.
- 45 GNATprove messages have no AdaLang kind mapping at all: tasking data
  races and the `Global`-aspect omission (14, expected — concurrency
  analysis is explicitly out of scope per `POSITIONING.md`), out-parameter
  initialization proofs (6), loop-unrolling/inlining diagnostics (16), and
  call-context analysis notes (9).

## Conclusion

This run's main finding remains `FP-040`, now closed rather than open: a
real, previously-unseen Libadalang property failure that escaped
`Finalize_Node`'s own containment, caught by external-corpus validation
exactly the way `quality/external_corpus_findings.md` intends. Fixing it
recovered most of `--verify`'s real obligation coverage on this corpus (44 to
680 obligations, `Proved_Safe` more than doubling) without changing a single
`Definite_Error`/`Proved_Safe` verdict that was already being reported —
the fix only affects whether an obligation gets registered at all, not what
it concludes once it is. The proof-agreement picture itself (7 matched
pairs, zero disagreement, most obligations still uncomparable to
`--mode=prove`) is consistent with SPARKNaCl's finding but remains too small
a sample to add confidence beyond it, and CubedOS's own unresolved
GNATprove findings mean it will likely never be as clean an oracle as
SPARKNaCl regardless. Re-running this benchmark as `--verify`'s relational
and interprocedural coverage grows is the natural next step.
