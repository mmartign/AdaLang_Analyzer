## The loop-variant fix: activated, but blocked short of `Proved_Safe` by an
## ordering-sensitivity gap in `Is_Leading_Invariant`

This corpus was re-run specifically because it has 26 `Loop_Variant`
pragmas — the first re-measured corpus with any meaningful count, after
five others this session came back a clean null result for lack of
eligible loops at all. The outcome here is a *different* kind of null
result: the mechanism visibly activates (10 stay `Unsupported`, unchanged
from before `a6239c1` existed; but 16 move from `Unsupported` to
`Unproved` — reclassified as "attempted, not discharged" rather than
flatly out of scope) — yet **zero of the 26 reach `Proved_Safe`.**

Root cause, confirmed with a minimal reproduction: every one of this
corpus's loops writes `pragma Loop_Variant` *before* its `pragma
Loop_Invariant`(s) — e.g.

```ada
pragma Loop_Variant   (Increases => Rnd_Len);
pragma Loop_Invariant (Chain_Len in 0 .. Chain'Length);
pragma Loop_Invariant (Rnd_Len in Rnd_Buffer'First .. Rnd_Buffer'Length);
```

`Is_Leading_Invariant` (`src/adalang_analyzer-flow_interp.adb`) decides
whether a `Loop_Invariant` is "leading" by walking the loop's statement
list from the top and requiring every preceding item to itself be a
`"loop-invariant"` pragma — a preceding `"loop-variant"` pragma fails that
walk immediately, so *neither* invariant above ever counts as leading, no
matter how simple its condition is. Loop-invariant preservation is
consequently never discharged for these loops (confirmed:
`Chain_Generator.adb`'s invariants are 0 `Proved_Safe` in this run), and
`Invariants_Usable_For_Variant` — the gate `a6239c1` added, requiring a
genuinely discharged leading invariant before variant progress is even
attempted — is never satisfied. This is asymmetric with the *variant's*
own leading check (`Is_Leading_Loop_Proof_Pragma`), which already tolerates
a mix of preceding `loop-invariant`/`loop-variant` pragmas in either
order; only the invariant side lacks the equivalent tolerance.

Reproduced directly: reordering a minimal two-pragma loop to put
`Loop_Invariant` first flips its preservation obligation from `Unproved`
("only leading loop invariants currently generate inductive verification
conditions") to `Proved_Safe`, with no other change. Ada/SPARK itself
attaches no semantic meaning to the relative order of `Loop_Variant` and
`Loop_Invariant` pragmas — GNATprove proves all of this corpus's variants
GNATprove attempts regardless of order (see `chain_generator.adb:467 loop
variant proved` in this run's own GNATprove output) — so this ordering
sensitivity is a gap in `Is_Leading_Invariant`, not a reflection of any
real Ada rule.

Not fixed in this session; recorded here as a precisely diagnosed
follow-up, the same way `RESULTS_2026-08-11.md`'s own "review targets"
section flagged open questions for later work.

## Follow-up fix, same day: `Is_Leading_Invariant` order tolerance (FP-050)

Fixed the ordering gap above. `Is_Leading_Invariant` and the sibling check
already used for `Loop_Variant`'s own leading status
(`Is_Leading_Loop_Proof_Pragma`) had become identical in everything but
which pragma kind(s) they tolerated as valid predecessors; deleted the
former and routed its one call site through the latter, which already
implements the correct, order-tolerant walk.

Re-verified against the same corpus checkout: total obligations, lane
timings, and the matched-pair bucket split are all **unchanged** from the
numbers above (`Proved_Safe` still 400, `Definite_Error` still 0). The
fix demonstrably activates, though — `Chain_Generator.adb`'s invariants
that previously reported "only leading loop invariants currently generate
inductive verification conditions" (the non-leading skip) now report "the
loop body does not establish invariant preservation" (a genuine SMT
attempt that failed for a real, separate, already-documented reason: the
guarded `if Rnd_Buffer (Rnd_Len) in Unbiased then ... end if;` inside
these loop bodies is a branch, and invariant preservation is documented as
supported only for straight-line bodies). So this corpus's zero
loop-variant `Proved_Safe` count is now attributable to that
straight-line-body limit alone, not to the ordering bug — a different,
correctly-attributed null result, not a fixed one. `sparknacl`, which also
consistently writes `Loop_Variant` before `Loop_Invariant`, shows the same
pattern when re-checked: the fix activates (same message-type shift) but
its own `Proved_Safe` count is also unchanged, blocked by its invariants'
own array-attribute complexity rather than this ordering bug.

Logged as `FP-050` in `quality/known_analysis_issues.tsv`; covered going
forward by `tests/verification_vc_variant_leading_invariant_order.adb`.

## Follow-up fix, same day: one-level `if`/`else` in loop bodies

Extended loop invariant preservation / loop variant progress to support a
loop body containing exactly one non-nested `if`/`else` (the `else` may be
omitted), where both branches independently reach the loop's back edge. The
CFG walk now forks at a `Condition_Node` with a `True_Edge`/`False_Edge`
pair, walks each arm under the same restricted rules as before, and — if
both arms reach the loop back edge — joins their final abstract/symbolic
state with the same `Flow_Join`/`VC.Join` machinery already used, and relied
on for soundness, at ordinary CFG merge points elsewhere in the tool. A
second sequential or nested branch, an `elsif` chain, or a `case` statement
still conservatively bail to `Unproved`, unchanged from before. New coverage:
`tests/verification_loop_branch_clean.adb` (positive, now `Proved_Safe` on
invariant preservation, variant progress, and postcondition),
`tests/verification_loop_branch_vc_broken.adb` (adversarial — branches
disagree on an invariant-tracked binding, stays `Unproved`, never a false
`Proved_Safe`), and `tests/verification_loop_branch_elsif_unsupported.adb`
(documents the `elsif` boundary), plus differential-corpus and
mutation-manifest wiring. Full repository gate (`sh tests/run_all.sh`)
passes.

Re-verified against the same `project_bias` checkout: **no change** to
`Proved_Safe` (400), `Definite_Error` (0), or any other total. This is a
precisely-attributable null result, not an inconclusive one. Every one of
this corpus's guarded loops (e.g. `Chain_Generator.adb:157`'s
`if Rnd_Buffer (Rnd_Len) in Unbiased then ... end if;`) writes an
array element inside the branch (`Chain (Chain_Len) := ...`), not just a
scalar — and a standalone reproduction confirms that a plain, unbranched
loop body containing the same kind of array-element write already fails
invariant preservation today, on `main`, independent of this fix (bails at
`Flow_Assigned_Name`, which only resolves scalar assignment targets). So
this corpus's loops were blocked by *two* independent limitations layered
together — the branch (now fixed) and the array write (still out of scope,
and always was: `SUPPORTED_VERIFICATION_SUBSET.md` has scoped loop
invariant preservation to a *scalar* body since before this session). Fixing
the branch alone cannot surface a `Proved_Safe` result while the array-write
limitation remains directly underneath it. Extending
`Flow_Assigned_Name`/the preservation walk to a supported class of
array-index writes would be a legitimate next step to actually move this
corpus's numbers, but is a separate, larger change than the one-level-branch
fix delivered here.

## Follow-up fix, same day: array-element and pointer-dereference writes in loop bodies

Delivered the array-write extension flagged above. An assignment whose
target `Flow_Assigned_Name` cannot resolve to a scalar name is no longer a
blanket walk-abort: if the destination is specifically an array-element/
slice write (`Ada_Call_Expr`) or a pointer dereference (`Ada_Explicit_Deref`),
the walk now skips only the *symbolic* update for that one statement (no
root can ever be planted for an indexed or dereferenced read — confirmed by
reading `Symbol_For`'s translation of `Ada_Call_Expr`, which always falls to
`Mark_Unsupported` for indexing) while still running the abstract
interpreter over it and continuing the walk, rather than aborting outright.
A record-component write (`Ada_Dotted_Name`) deliberately keeps aborting:
unlike an array element, `Obj.Field` reads *are* symbolically tracked with
their own root, so skipping the update there would let a later reference
resolve to a stale pre-write value — a real soundness trap, not just an
imprecision. New coverage: `tests/verification_loop_array_write_clean.adb`
(positive, now `Proved_Safe`) and
`tests/verification_loop_record_write_unsupported.adb` (adversarial —
confirms the record-component exclusion still holds, both before and after
this change). Full repository gate passes.

Re-verified against the same `project_bias` checkout: **still no change**
to `Proved_Safe` (400) or `Definite_Error` (0), but the failure mode for
this corpus's loops moved and is now precisely, differently attributable.
Before this fix, `Chain_Generator.adb:234`'s
`Chain_Len in 0 .. Chain'Length` invariant failed preservation with
`imprecisionSource: "the scalar loop preservation VC was not discharged"`
(the walk never got past the array write). After this fix, the walk gets
further and the same obligation now fails with
`reasonCode: "missing-static-bounds"`, `blockingExpression: "Chain'Length"`
— a third, independent limitation: `Chain` is `Alphanumeric_Mixed`, a
`subtype ... is String` with only a `Dynamic_Predicate`
(`Chain_Generator.ads:12`), i.e. an unconstrained array parameter whose
`'Length` is a genuine runtime value, not a static constant, and the scalar
bounds machinery only resolves *static* bounds today. This is systemic
across the corpus (315 of 2,316 obligations carry
`reasonCode: "missing-static-bounds"` in this run), not specific to these
loops. Both fixes delivered today are independently sound and independently
tested, but neither the branch fix nor the array-write fix can surface a
`Proved_Safe` result here while this third, separate limitation —
symbolically tracking `'Length`/`'First`/`'Last` of an unconstrained array
parameter as a dynamic-but-stable bound — remains unaddressed. That would be
a materially larger change (touching how bounds are resolved throughout the
range-check/overflow machinery generally, not just the loop-preservation
walker) and was not attempted in this session.

## Follow-up fix, same day: symbolic `'Length` for unconstrained array parameters

Delivered the bound-resolution extension flagged above, scoped to
`'Length` specifically (the attribute the corpus's own obligations
actually reference; `'First`/`'Last` on an unconstrained array object
remain unsupported, unchanged). `Integer_Term`'s `Ada_Attribute_Ref` case
(`src/adalang_analyzer-vc_prover.adb`) now falls back to a fresh symbol,
lower-bounded at `0` — the one fact the language itself guarantees about
any array's length, regardless of what the object's actual bounds turn out
to be — instead of stopping translation, whenever `'Length`'s object
bounds aren't statically known. `Add_Root`/`Symbol_For` gained a small
`Explicit_Bounds` parameter to carry this the same way `Enum_Bounds`
already does for enumeration roots. New coverage:
`tests/verification_loop_length_symbolic_clean.adb` (positive) and
`tests/verification_length_attribute_unsound.adb` (adversarial — confirms
the fresh symbol proves `'Length >= 0` but never the unwarranted
`'Length >= 1`, i.e. the bound is exactly what the language guarantees, no
tighter). Full repository gate passes.

Re-verified against the same `project_bias` checkout: `Proved_Safe` rose
400 → **414** (+14), `Definite_Error` still 0. This is real, not noise —
confirmed by checking obligation-by-obligation, not just the aggregate.
However, tracing precisely *which* obligations moved shows the `+14` are
ordinary range-check/assertion obligations elsewhere in the corpus that
reference `'Length` directly; the `loop-invariant-preservation`/
`loop-variant` proved-safe counts for `Chain_Generator.adb`'s guarded loops
are still exactly 0 — this fix alone does not touch them.

Digging into why (five stacked synthetic reproductions, from a plain
straight-line dynamically-bounded counter down to the exact corpus shape)
isolated a **fourth, and deeper, limitation**: `Chain_Generator.adb`'s
actual `if Rnd_Buffer (Rnd_Len) in Unbiased then Chain_Len := Chain_Len +
1; ... end if;` has no `else` — `Chain_Len` is incremented on one arm and
left untouched on the other. Loop preservation's branch-merge (this
session's first fix) is working exactly as designed here: since the two
arms' terms for `Chain_Len` genuinely disagree, `VC.Join` correctly
introduces a fresh, *totally unconstrained* symbol for the merged value —
the same conservative behavior already relied on for soundness at every
ordinary CFG merge point in the tool, and the same behavior this session's
own adversarial fixture (`verification_loop_branch_vc_broken.adb`) was
written to confirm. But it means the merged `Chain_Len` carries no relation
at all to its pre-branch value or to `Chain'Length`, so `Chain_Len' in 0 ..
Chain'Length` is genuinely not provable from the merged state — regardless
of the `'Length` symbol now being available. This was confirmed directly:
a synthetic loop with this exact asymmetric-branch shape (dynamically-
bounded counter, incremented on only one arm, guarded so the increment is
actually safe) reproduces the identical `Unproved` outcome the real corpus
shows. A fifth, narrower gap was also found in passing: the corpus's loop
variants (e.g. `Rnd_Len : size_t range Rnd_Buffer'First ..
Rnd_Buffer'Length`) are *also* dynamically bounded, and variant-progress
bound resolution (`Overflow_Base_Range`/`Type_Range` in
`flow_interp.adb`/`flow_eval.adb`) is a separate abstract-domain code path
this session's `'Length` fix did not touch — it would need an analogous
extension to stop independently blocking variant progress even if the
join-precision issue above were fixed.

Closing the fourth limitation for real — proving an invariant across an
asymmetric branch when the tracked value differs between arms — is not a
narrow extension like the three delivered today. It needs the merged value
represented as an SMT if-then-else term conditioned on the branch's own
predicate (`(ite <cond> <true-term> <false-term>)`) instead of a forgotten,
fresh symbol, which is a different and larger design than reusing the
existing term-equality `VC.Join`/`Flow_Join` this session leaned on for
its soundness argument each time. That is a substantial, independent piece
of architecture work and was not attempted here.

## Follow-up fix, same day: base-range fallback for dynamically-constrained non-derived subtypes

Attempted the fifth gap flagged above: `Overflow_Base_Range`
(`src/adalang_analyzer-flow_interp.adb`) previously bailed to `Unknown_Range`
for *any* non-derived subtype (`Is_Null` on `P_Base_Type`, which Libadalang
defines only for `type X is new Y` derivations) — including an ordinary
object declaration whose own constraint is dynamic, e.g. `Rnd_Len : size_t
range Rnd_Buffer'First .. Rnd_Buffer'Length`. It now falls back to
`Typ.P_Base_Subtype`, which Libadalang already recurses through arbitrary
further subtype chains to reach the type's own fully-unwound base
declaration (confirmed by reading its generated body), and calls
`Type_Range` on *that* instead of giving up. Ada scalar subtyping only ever
narrows, so this is always a sound, if looser, overapproximation. New
coverage: `tests/verification_loop_variant_dynamic_bound.adb`, asserting
the `missing-static-bounds` reason code no longer fires for this shape.
Full repository gate passes.

This is a real, confirmed fix — direct before/after testing on an isolated
fixture (`Chain_Len : Natural range 0 .. Chain'Length`, straight-line body,
no branch) shows `loop-variant`'s `reasonCode` genuinely changes from
`missing-static-bounds` to empty, meaning `Decide_Variant_Progress` now
gets *past* the bounds gate and attempts the SMT proof, where before it
refused outright. It is not, however, a proof: on that same isolated
fixture, the SMT solver still doesn't discharge strict progress, for a
reason not root-caused in this session (a sixth, still-open question).

**Re-verified against `project_bias`: zero change** — confirmed with a
careful, clean before/after A/B (checkout the pre-fix commit, rebuild, run;
checkout the fix, rebuild, run), not just eyeballing a summary number. The
two full JSON outputs are obligation-for-obligation identical
(`cmp` byte-identical, in fact, once compared against a correctly fresh
baseline — an earlier same-session comparison against a stale cached result
had wrongly suggested a 74-obligation improvement; that was an artifact of
not regenerating the baseline, not a real effect, and is corrected here).
The reason for zero impact is now understood precisely: `Mark_Variant_Progress`
gates the entire `Overflow_Base_Range`/`Decide_Variant_Progress` call behind
`Invariants_Usable_For_Variant`, which is false for `Chain_Generator.adb`'s
loops because their leading invariant is still unproved (the fourth
limitation, above, not this session's to close). This fix's code path is
therefore never reached for this corpus's own obligations at all — it is
correct, tested, real groundwork for the *next* fix (closing the fourth
limitation), not a fix that pays off on its own here.

Kept and committed on its own merits (sound, regression-tested, a genuine
capability gap closed for any dynamically-constrained-but-statically-typed
loop-variant or overflow check not gated by a separate undischarged
invariant), with this outcome recorded plainly rather than implied to have
moved the corpus's numbers.
