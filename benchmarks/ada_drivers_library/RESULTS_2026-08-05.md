## Confirmed AdaLang precision problem: FP-042

The first `--automotive` run reported:

```
stm32-sdmmc.ads:38:1: warning: circular dependency: stm32-sdmmc.ads ->
stm32-sdmmc_interrupt.ads -> stm32-sdmmc.ads [Circular_Package_Dependency]
```

`stm32-sdmmc.ads` does `with STM32.SDMMC_Interrupt;` (ordinary), but
`stm32-sdmmc_interrupt.ads` does `limited with STM32.SDMMC;` — not an
ordinary with. A `limited with` gives only an incomplete view and imposes no
"elaborate before" requirement; RM 10.1.2 permits it specifically so two
units can reference each other's types without a real circular elaboration
dependency, and `SDMMC_Interrupt_Handler`'s protected-type discriminants use
exactly that idiom to reference `STM32.SDMMC`'s controller type back. This
is not a defect in the driver library; it is `Circular_Package_Dependency`
building its with-graph edges from `Compilation_Unit.P_Withed_Units`, which
does not distinguish a limited with from an ordinary one.

Reproduced minimally (two spec files, no bodies):

```ada
with B;
package A is
   type Ref is access all B.Info;
end A;
```
```ada
limited with A;
package B is
   type Info is null record;
   type Back_Ref is access all A.Ref;
end B;
```

Flagged before the fix, clean after. Fixed by building edges from
`Compilation_Unit.F_Prelude`'s own `With_Clause` nodes instead of the
aggregated `P_Withed_Units`: each non-limited clause's `F_Packages` names are
resolved individually via `P_Referenced_Decl (Imprecise_Fallback => True)`
to reach the target unit's filename, and any clause with `F_Has_Limited`
true contributes no edge at all. Confirmed the existing real-cycle
regression (`circular_dependency_findings_a.ads`/`_b.ads`, an ordinary
mutual with, no limited view on either side) still fires unchanged, and the
full test suite (`tests/run_all.sh`) passes unchanged. Regression:
`tests/circular_dependency_limited_with_a.ads`/`_b.ads`, run by
`run_circular_dependencies.sh`. See `FP-042` in
`quality/known_analysis_issues.tsv`.

`--automotive`'s finding count above (1,973) is the corrected, post-fix
count; the pre-fix run reported 1,974.

## Concurrency-prohibition checks: validated against real tasking code

The question this benchmark exists to answer. `arch/ARM/STM32/drivers/` has
7 files declaring `protected` types or objects (interrupt-driven DMA, RNG,
SD/MMC, and LTDC display-sync handlers) and zero declaring `task`:

| Rule | Findings | Assessment |
| --- | ---: | --- |
| `No_Tasking` | 0 | True negative — no `task type`/`single task` anywhere in the corpus; only `protected`, which this rule does not cover by design |
| `No_Rendezvous` | 5 | True positive — every `entry` declaration in the corpus, confirmed by manual review (see below) |
| `No_Select` | 0 | True negative — a `select` statement needs a `task` body; none exist here |
| `No_Requeue` | 0 | True negative — same reason |
| `No_Asynchronous_Transfer` | 0 | True negative — same reason |
| `Potentially_Blocking_Operation` | 0 | True negative — none of the 7 protected bodies' operations call `delay` or an entry; a correct ISR must not block, and this library's interrupt handlers correctly don't |

All 5 `No_Rendezvous` findings, manually confirmed as real `entry`
declarations, not `accept` statements (there are no `task` bodies to have
one):

- `dma2d/stm32-dma2d-interrupt.adb:44`
- `dma_interrupts/stm32-dma-interrupts.ads:54`
- `ltdc/stm32-ltdc.adb:151`
- `sd/stm32-sdmmc_interrupt.ads:55`
- `stm32-rng-interrupts.adb:60`

`No_Tasking`/`No_Select`/`No_Requeue`/`No_Asynchronous_Transfer` all reading
zero is a real result, not an untested check: this particular driver subset
happens to be protected-object-only, idiomatic Ravenscar interrupt handling
rather than a multi-task design. It confirms these checks correctly stay
silent on legitimate protected-object code (they do not, for instance,
mistake a protected `entry` for a task rendezvous the way a naive text match
might), but a corpus that also exercises real `task` declarations, `select`
statements, and `requeue` would be needed to see `No_Tasking`/`No_Select`/
`No_Requeue`/`No_Asynchronous_Transfer` fire true positives the way
`No_Rendezvous` did here.

## Other findings, spot-checked

- **`No_Dispatching_Call`: 18.** Not all tagged-type dispatch: 16 of the 18
  are calls through `access procedure`-typed callback variables (e.g.
  `dma2d/stm32-dma2d.adb`, `DMA2D_Wait_Transfer_Int.all;`, an
  interrupt-completion callback pointer), which this rule's own documented
  scope explicitly covers alongside tagged dispatch ("dynamically
  dispatching and access-to-subprogram calls whose target cannot be
  determined from local syntax") — working as designed, not a surprise.
  The remaining 2 (`stm32-setup.adb:48,83`) are genuine tagged-type calls.
- **`Magic_Number`: 740, `Complete_Initialization`: 380.** The two largest
  counts by far, both plausible rather than surprising for this code shape:
  register-level hardware drivers are dense with numeric constants (bit
  masks, clock dividers, peripheral base offsets) and locals that receive a
  hardware register's value rather than an explicit literal — spot-checked
  a handful of each (e.g. `crc_stm32f4/stm32-crc-dma.adb:138`,
  `devid_stm32f4/stm32-device_id.adb:43,55`) and found nothing resembling a
  false positive, just a strict rule meeting a code style that doesn't
  follow its discipline.
- **`Missing_Depends_Contract`: 309**, the largest `--spark` count, is
  expected on any pre-SPARK codebase (only 2 of 90 files set `SPARK_Mode`):
  ordinary Ada procedures have no `Depends` contract to check against by
  construction.

## Conclusion

This benchmark's primary purpose — real-code evidence for the six
`--automotive`-only concurrency-prohibition checks, previously validated
only against hand-constructed `quality/precision_corpus.tsv` fixtures — is
met: `No_Rendezvous` correctly fires on every real `entry` in the corpus,
and the other five correctly stay silent on code that (correctly, for a set
of ISRs) contains nothing for them to catch. Its secondary purpose, the same
one every corpus in this directory has served, also paid off: it surfaced a
real, previously-unknown false positive (`FP-042`, a `limited with`
misclassified as an ordinary circular dependency), fixed as part of
recording these results, with zero regressions across the full test suite.
The main limitation is the one noted above — this specific driver subset
exercises `protected` objects thoroughly but not `task`/`select`/`requeue`
at all, so those three checks' true-positive behavior on real code remains
unconfirmed. A different Ada_Drivers_Library subset or a second corpus with
genuine multi-task designs would be the natural next step to close that gap.
