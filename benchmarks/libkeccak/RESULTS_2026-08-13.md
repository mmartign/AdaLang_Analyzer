# Libkeccak comparison results — 2026-08-13

## Environment and scope

- damaki/libkeccak: `4b7174fccbf5461998b18395aaeecc68bb25798d`
- AdaLang Analyzer: `1.0.0-rc1`, commit `f8a0375fd3fcf13e72356e08018d7f60db12df7d`,
  incorporating two commits landed today relative to the `RESULTS_2026-08-07.md`
  baseline (commit `681844c098ffb2d846b61a0253753c5c85e7e488`):
  - `a6239c1` "Prove bounded loop variant progress" — `VC_Prover` now
    discharges one leading, single-component `Increases`/`Decreases`
    `Loop_Variant` as `Proved_Safe` when both the entry and back-edge values
    stay within the expression's base type's *static* bounds (previously
    loop variants were enumerated/reachability-checked only and never
    yielded `Proved_Safe`).
  - `f8a0375` "Resolve symbolic scalar sorts semantically" — `Assign` now
    resolves a scalar's SMT sort (`Bool`, `Int`, or `Enum_Sort`) from
    Libadalang's own declaration instead of guessing Boolean first, closing
    a soundness gap for enum-typed assignments and fixing a class of
    `sort-mismatch` misclassifications.
- GNATprove: FSF 16.1.0, Why3 1.8.2+git, CVC5 1.3.2, Z3 4.15.4, Alt-Ergo 2.6.1
  (bit-identical toolchain to the baseline)
- Compiler: Alire `gnat_native` toolchain (this repository's own pin)
- Host: Apple Silicon (arm64), macOS 26.5.2, 14 logical cores
- Project: `libkeccak.gpr -XLIBKECCAK_ARCH=generic -XLIBKECCAK_SIMD=none`, 100
  source files under `src/common/` and `src/generic/`, analyzed by both tools
- GNATprove ran with `-P libkeccak.gpr -XLIBKECCAK_ARCH=generic
  -XLIBKECCAK_SIMD=none --mode=prove -f -q --output=oneline
  --prover=z3,cvc5,altergo`, the same CVC4→CVC5 toolchain override as the
  baseline (see `benchmarks/libkeccak/README.md`, "Toolchain override"); the
  project's own `--steps=16000 --timeout=60` budget was used unmodified

**Libkeccak is still fully proved at this configuration.** GNATprove's own
summary (`benchmark-results/libkeccak/gnatprove.out`) reports 21,077 total
checks, 0 unproved, 78 justified (0%) — bit-identical to the 2026-08-07
baseline. That is expected: neither of today's two commits touches
GNATprove or the corpus, only AdaLang's own `--verify` lane, so the oracle
side of this comparison is unaffected and remains trustworthy.

**Timing caveat.** This run shared the host with several other benchmark
`run.sh` invocations executing concurrently (sparknacl, tokeneer,
coap_spark), all competing for the same 14 logical cores — over 190
`gnatwhy3`/`gnatprove` worker processes were observed running simultaneously
partway through this run. AdaLang's own lane took 137.3 s (real) here versus
11.6 s in the uncontended 2026-08-07 baseline, and GNATprove's `--mode=prove`
lane took 806.2 s versus 334.9 s. Both lanes still produced correct,
complete output (exit status 0, and GNATprove's own summary is unchanged
from baseline), so the results below are not in question — only the
wall-clock timing numbers are not a like-for-like performance comparison
this time, and should not be read as an analyzer performance regression.

## Delta analysis: which commit explains the movement?

libkeccak is, as `benchmarks/libkeccak/README.md` describes it, "a
sponge-construction hash family built from generic permutation cores
instantiated many times over varying state sizes, with loops throughout" —
on paper a strong candidate for the loop-variant fix. The actual obligation
data says otherwise: **the `Proved_Safe` gain is not attributable to
`a6239c1`.**

### `loop-variant`: zero movement — a genuine null result

All 23 `loop-variant` obligations in this run remain non-safe (15
`Unproved`, 8 `Unsupported`); none are `Proved_Safe`. Inspecting the
corpus's own `pragma Loop_Variant` clauses explains why, precisely along the
lines the commit's own documented scope predicts:

- **20 of the 23** use a compound, multi-component variant — e.g.
  `keccak-generic_keccakf-byte_lanes.adb:161`: `pragma Loop_Variant
  (Increases => Offset, ...)` continuing onto further criteria. `a6239c1`'s
  documented scope is explicitly "one leading, **single-component**
  `Increases` or `Decreases`" — these fall outside it by construction, and
  AdaLang's own `explanation`/`reasonCode` fields confirm this
  (`unsupported`/`unproved` status, not a proof attempt that failed).
- The remaining **2** (`keccak-generic_hash.adb:90` and
  `keccak-generic_xof.adb:89`, both `pragma Loop_Variant (Decreases =>
  Remaining)`) *are* single-component and were genuinely eligible — and
  both remain `Unproved`, with `reasonCode: missing-static-bounds` and
  `explanation: "loop-variant progress is not discharged"` /
  `imprecisionSource: "the required bounds are not statically known"`.
  `Remaining`'s base type does not have statically known bounds tight
  enough for the fix's required finite-bound argument, so this exact
  eligible case still doesn't discharge.

This is a plain null result, not a story invented to fit expectations: the
fix works exactly as scoped, and libkeccak's loop-variant style (compound
criteria; a `Remaining`-style counter without static bounds) simply doesn't
intersect that scope.

### The `Proved_Safe` gain is consistent with `f8a0375`

With `a6239c1` ruled out by direct obligation inspection, attention turns to
`f8a0375`. This run's `Proved_Safe` obligations are dominated by
`initialization-check` (1,755 of 2,711), with `index-check` (497),
`range-check` (181), `division-by-zero` (261), `integer-overflow` (14), and
`loop-invariant-initialization` (3) making up the rest. No baseline
per-kind snapshot survives to diff this against directly (see caveat below),
so the +572 total cannot be decomposed kind-by-kind — but the *qualitative*
case for `f8a0375` explaining it is strong on this corpus specifically:

- libkeccak's generic sponge/hash/XOF/cSHAKE/KMAC/TupleHash/ParallelHash
  units are all built around an explicit `type States is (...)` enumeration
  (e.g. `Absorbing`/`Squeezing`/`Finished`, `Updating`/`Extracting`/
  `Finished`) that is assigned and compared throughout every operation on
  every one of the corpus's many generic instantiations — exactly the
  enum-assignment pattern `f8a0375` targets (`Assign` now resolves
  `Enum_Sort` from the declaration instead of defaulting to a Boolean
  guess).
- `reasonCode: sort-mismatch` still accounts for 209 of the remaining
  non-safe obligations in this run — a residual, not a full closure: the
  fix's own regression coverage is scoped to enum-literal assignment,
  enum-variable copying, membership, and `True`/`False`-named literals, not
  every scalar-sort pattern. That 209 remains nonzero is itself evidence the
  fix is doing real, bounded work rather than something that would have
  zeroed out this reason code entirely.
- GNATprove's own oracle output is unchanged (still 21,077/0/78), ruling out
  any oracle-side or corpus-side explanation for the AdaLang-side movement.

**Caveat on attribution precision:** this repository does not retain a
per-obligation-kind breakdown from the 2026-08-07 baseline run (only the
aggregate summary in `RESULTS_2026-08-07.md`), so the +572 cannot be
decomposed kind-by-kind against a prior snapshot. The reasoning above is
based on (a) ruling out `a6239c1` by direct inspection of every
`loop-variant` obligation's outcome and blocking reason in this run, and (b)
the corpus's own heavy, corpus-wide use of the exact enum-assignment idiom
`f8a0375` is documented to target, corroborated by the nonzero-but-reduced
`sort-mismatch` residual. It is not a claim that every one of the 572 newly
`Proved_Safe` obligations is individually traceable to an enum assignment.

## Caveats

- Timing figures in this run are not comparable to the 2026-08-07 baseline
  due to heavy host contention from concurrently running benchmark
  harnesses — see "Timing caveat" above. Correctness of the output (exit
  codes, GNATprove's own unchanged summary) is not in question.
- Prover/solver versions are bit-identical to the baseline (recorded above
  and in `benchmark-results/libkeccak/gnatprove.out`).
- Libkeccak's proofs cover run-time-error freedom only (SPARK silver level),
  not functional correctness; this comparison is scoped to the same
  run-time-error obligation category `--verify` targets.
- The GNATprove message-text substring matching in `compare.awk` is a
  heuristic against observed wording, not a stable GNATprove API — see
  `benchmarks/sparknacl/README.md`'s caveat for the same point.
- No per-kind breakdown of the 2026-08-07 baseline was retained, so the
  attribution of the `Proved_Safe` gain to `f8a0375` above is qualitative
  (corroborated by direct inspection of this run's data and by ruling out
  `a6239c1`), not a kind-by-kind before/after diff.

## Bottom line

Libkeccak remains fully proved by GNATprove at this configuration, and
AdaLang's two headline-risk buckets remain at zero: no possible unsoundness,
no false positives, unchanged from baseline. Today's two commits move the
needle by a real +572 `Proved_Safe` obligations (2,139 → 2,711, roughly a
27% relative increase) with the matched-pair set moving in the same
direction (+3 both-safe). Of the two commits, the evidence in this run
attributes that gain to `f8a0375` (symbolic scalar sort resolution) — this
corpus's pervasive `States` enumeration idiom is exactly its documented
target, and a nonzero-but-reduced `sort-mismatch` residual (209) is
consistent with bounded, real progress rather than a full closure.
`a6239c1` (loop variant progress) demonstrably contributes **nothing** on
this corpus: every one of libkeccak's 23 `loop-variant` obligations remains
non-safe, split between being structurally out of the fix's documented
single-component scope (20 of 23, compound variants) and structurally
in-scope but blocked by non-static bounds on the variant expression itself
(the remaining 2). That is a plain, evidence-backed null result for this
corpus, not a story stretched to fit the "loops throughout" framing the
corpus's own README invites.
