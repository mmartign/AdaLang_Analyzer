## GNATprove boundary

`--mode=flow` on the unmodified project reaches 41 units (20 entities flow
analyzed, 287 explicit `SPARK_Mode => Off` skips) before erroring out:

```text
gnatcoll-strings.ads:31:01: error: instantiation error at gnatcoll-strings_impl.ads:318
gnatcoll-strings.ads:31:01: error: function associated to aspect Iterable with dependency on globals is not allowed in SPARK
gnatcoll-strings.ads:31:01: error: delayed type aspect on "XString" is required to be in SPARK
gnatprove: error during analysis of data and information flow
```

`GNATCOLL.Strings`'s `XString` type uses an `Iterable` aspect whose
dependency-on-globals shape SPARK's own legality rules reject outright, the
same category of "the project itself was never written with SPARK analysis
in mind" boundary AWS hit (`aws-client-http_utils.adb`'s `Discard_Names`
attribute) and Ada_Drivers_Library's untried-by-design bare-metal driver
tree — not a partial/degraded run, a hard stop, since `gnatcoll-strings.ads`
sits early enough in the project's own dependency order that nothing after
it gets a flow result either. AdaLang's `--verify`, in contrast, completed
its full 154-file pass in 11.56 s with no such boundary: enumerating,
proving, or declaring unsupported every scalar obligation it reaches,
regardless of whether the surrounding code was ever meant to be SPARK.

## Confirmed analyzer mistake (fixed): FP-043

Both of `--verify`'s `Definite_Error` outcomes on the baseline run were the
same false positive: `flow_interp.adb`'s `Initialization_Read_Required`
(the bounded verifier's own identifier-classification walk, independent of
`Checks.Data_Flow`'s separate `Uninitialized_Read` walk, which already had
this exact guard) treated a pragma argument naming an entity ("Status" in
`pragma Unreferenced (Status);`) as a genuine read, at both
`GNATCOLL.OS.FS.Close` (`gnatcoll-os-fs.adb:41`) and
`GNATCOLL.Plugins.Unload` (`gnatcoll-plugins__unix.adb:76`):

```ada
procedure Close (FD : File_Descriptor) is
   function C_Close (FD : File_Descriptor) return int;
   pragma Import (C, C_Close, "close");
   Status : int;
   pragma Unreferenced (Status);
begin
   Status := C_Close (FD);
end Close;
```

`Status`'s real initializing assignment is two statements after the
`Unreferenced` pragma that named it; the walk misread the pragma argument
as a read before that assignment. Fixed by adding the identical
pragma-argument guard `Checks.Data_Flow` already had (excluding
`unreferenced`/`unmodified`/`warnings` pragma arguments from counting as a
read) to `Initialization_Read_Required` as well. Confirmed on the real
corpus: both `Definite_Error` outcomes are gone (0 remaining), and
`--verify`'s total obligation count fell from 5,107 to 5,043 — the 64-
obligation drop reflects the corpus's other 69 `pragma Unreferenced`
occurrences (mostly on already-initialized parameters, so not
`Definite_Error`-producing, but still spuriously enumerated as obligations
at the pragma before the fix). Regression:
`tests/verification_initialization_pragma_unreferenced_clean.adb`, run by
`run_verification.sh`. See `quality/known_analysis_issues.tsv` (`FP-043`)
for the full root-cause writeup.

## Confirmed analyzer mistake (fixed): FP-045

All 18 of the baseline `--recommended` run's `Reversed_Range` findings,
spread across 11 files, were the same false positive: the rule flagged any
static range with `Low > High` unconditionally, including Ada's own
idiomatic spelling of a statically empty array or range, `Low .. Low - 1`
(here always literally `1 .. 0`):

```ada
return (1 .. 0 => <>);                                     --  empty result
No_Args : constant GNAT.OS_Lib.Argument_List := (1 .. 0 => null);
Null_Char_String : constant Char_String := (1 .. 0 => <>);
```

None of these are swapped-bounds mistakes. Fixed by excluding exactly
`Left_Int.Value = Right_Int.Value + 1` from the check (`checks-
expressions.adb`), alongside the existing `Left_Int.Value > Right_Int.Value`
gate: a genuinely reversed range (a real typo, e.g. `10 .. 1` meant to be
`1 .. 10`) almost never happens to land exactly one short of empty, so a
wider gap between the bounds is still flagged unchanged, and the existing
precision-corpus "5 .. 1" fixture (a gap of 4) is unaffected. Confirmed on
the real corpus: all 18 findings are gone (0 remaining), with no other
rule's counts affected. Regression:
`tests/precision_reversed_range_empty_idiom_clean.adb`, added to
`quality/precision_corpus.tsv` and run by `run_precision_corpus.sh`. See
`quality/known_analysis_issues.tsv` (`FP-045`) for the full root-cause
writeup.

## Root-caused and fixed at the mechanism level, findings unchanged: FP-044

Spot-checking the remaining 49 `Uninitialized_Output` findings turned up a
second false-positive shape, distinct from FP-043/FP-045:
`GNATCOLL.Buffer.Current_Text_Position`'s `Line`/`Column`
(`gnatcoll-buffer.adb:57-58`), a same-named-overload out-parameter-
forwarding call (the 3-formal overload forwards positionally to the
4-formal one). This is the same general shape `FP-021` already fixed once
(Ada_Drivers_Library's HM11 driver), but a deeper gap in the *retry* path
that fix relies on: when the primary resolution lands on the wrong (self,
enclosing) overload and that wrong overload happens to still have a formal
at the same actual position, `Callee_Formal_At_Position`/
`Callee_Formal_By_Name` trusted it anyway instead of falling through to
the `Callee_Candidate_By_Arity` retry that exists precisely to catch this;
separately, that retry's own `Call.F_Name.P_All_Env_Elements` call used
Libadalang's default `Seq => True`, which excludes a sibling overload
declared later in the same package spec even though the whole spec is
visible to every one of its own bodies. Both fixed in a later pass on this
same corpus: an arity gate now rejects the primary resolution whenever the
call has more actuals than it has formals (relaxed to that, rather than
requiring an exact count match, after an early stricter version broke
genuinely-resolved calls to a callee with a trailing defaulted formal
omitted from the call — confirmed live on this corpus's own `Full_Parse`
calls, `gnatcoll-email-parser.adb`), and the arity retry now passes
`Seq => False`. See `quality/known_analysis_issues.tsv` (`FP-044`, closed)
for the full trace.

Confirmed by re-running this benchmark after the fix: every finding count
above is unchanged (132/898/898 across the three presets, `Line`/`Column`
still both flagged at `gnatcoll-buffer.adb:57-58`) — because this specific
call sits inside a unit where a separate, still-open, pre-existing
"dereferencing a null access" Property_Error (`GNATCOLL.Buffer`'s own
`use all type FS.File_Descriptor;`, the same general class of upstream
Libadalang defect as `FP-029`, just triggered by a plain private derived-
`Integer` type rather than an `Interfaces`-derived one) fires earlier in
the same call's resolution chain and keeps `Callee_Formal_At_Position` from
ever being reached for it, so the FP-044 fix has no visible effect on this
corpus specifically. The fix was instead confirmed live elsewhere in this
same corpus (`Callee_Candidate_By_Arity`'s `Best_Of_Kind` sees more than
one candidate at several call sites, e.g. `gnatcoll-email.adb`'s
`Next (C);`, whose primary resolution wrongly lands on an unrelated
2-formal same-named `Next` elsewhere in scope) and by the precision-corpus
regression pair `uninitialized_output_overload_defaulted_trailing_clean/
guard.adb`.

Distinct from this, and *not* a new limitation: most of the corpus's other
`Uninitialized_Output` findings forward a `Success`/`Status` actual to a
`System.OS_Lib` (`GNAT.OS_Lib` renames it) runtime procedure such as
`Rename_File` or `Copy_File`, each declared twice in the GNAT runtime (once
for `String`, once for `C_File_Name`) at the *same* arity. The arity-only
fallback correctly refuses to guess between two same-arity candidates by
design (the same already-accepted class as `FP-008`/`FP-012`/`FP-018`/
`FP-021`) — not investigated further, the same call this project's own
prior benchmarks made for their own residual `Uninitialized_Output`
findings (Ada_Drivers_Library's `RESULTS_2026-08-05.md`: "not investigated
further as a false positive").

## Interpretation

Like AWS, `gnatcoll-core` validates AdaLang's standalone breadth and
precision on ordinary Ada that was never written with SPARK analysis in
mind, not agreement with a GNATprove oracle: GNATprove hard-stops on a
SPARK-illegal `Iterable` aspect 41 units into the project, while AdaLang
completes a full 154-file `--verify` pass in 11.56 s regardless. This is
the fifth real-corpus run to find and fix genuine analyzer false positives
(after `FP-019`/`FP-020` on AWS, `FP-039` on SPARKNaCl, `FP-040` on
CubedOS, `FP-042` on Ada_Drivers_Library) and, with `FP-045`, the first to
find one in an ordinary-findings rule (`Reversed_Range`) rather than the
bounded verifier or a cross-cutting dependency check — a reminder that
`--recommended`'s plain lint-style rules are exercised by real, unfamiliar
code just as unevenly as `--verify`'s proof engine is.
