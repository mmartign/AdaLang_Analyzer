## Agreement: matched obligations

Matched by `(file, line, check kind)` — see `benchmarks/sparknacl/README.md`
for the matching design and why unequal-count locations are reported
separately rather than guessed. 886 obligations matched 1:1:

| Bucket | Count | Meaning |
| --- | ---: | --- |
| Both safe | 32 | AdaLang `Proved_Safe`, GNATprove proved |
| AdaLang conservative | 850 | AdaLang `Unproved`/`Unsupported`, GNATprove proved |
| **Possible AdaLang unsoundness** | **0** | AdaLang `Proved_Safe`, GNATprove NOT proved |
| **AdaLang false positive** | **0** | AdaLang `Definite_Error`, GNATprove proved |
| Both flag a problem | 4 | Both non-safe |

Zero obligations in the two headline-risk buckets: AdaLang never called
something safe that GNATprove could not prove, and never called something a
definite error that GNATprove proved safe, anywhere in the matched set. The
4 "both flag a problem" cases are exactly GNATprove's own 4 of its 9
residual unproved checks that also have a 1:1 AdaLang counterpart, and
AdaLang independently reports each as `Unsupported` rather than pretending
to resolve them — e.g. `sparknacl-sign.adb:589`, a loop-invariant
preservation obligation GNATprove's provers give up on after a step-limit;
AdaLang's bounded, non-relational domain has no way to prove it either, and
says so honestly instead of guessing.

Coverage-only counts (not compared, not errors):

- 5,297 AdaLang obligations have no GNATprove `--mode=prove` counterpart for
  that kind — dominated by `initialization-check` (2,424), which is a
  flow-analysis result outside `--mode=prove`'s output.
- 349 GNATprove checks (of mapped kinds) have no AdaLang obligation at the
  same location — mostly `range-check` (267), largely from `.ads` spec files
  AdaLang does not currently emit obligations for on their own.
- 939 GNATprove messages have no AdaLang kind mapping at all: initialization
  proofs (flow, ~280 occurrences), `Always_Terminates` proofs (~60),
  `data dependencies proved` (198), `length check`/`predicate check`/
  `contract case` proofs, and out-parameter-after-call flow checks — all
  outside what AdaLang's bounded verifier currently attempts. This is
  consistent with `POSITIONING.md`: AdaLang's `--verify` classifies "a much
  narrower scalar subset" than GNATprove's full verification-condition
  pipeline, not an equivalent one.
- 220 locations have a different obligation count on each side (usually
  AdaLang recording 2 for GNATprove's 1, e.g. most `precondition` mismatches
  — a known, already-catalogued shape: `FP-033` records a call's
  precondition under two distinct stable IDs, the whole call and just the
  callee name) and are intentionally left unpaired for manual review rather
  than guessed.

## Confirmed AdaLang precision problem: FP-039

The first real run (before the fix below) reported `definiteError: 48`
overall. Every one of the 48 turned out to be the identical bug: `x0`..`x15`
and `j0`..`j15`, named in `sparknacl-core.adb`'s `ChaCha20_Encrypt_Bytes`
inside three nested procedures' (`Quarter_Rounds`, `Assign_X_To`,
`Update_Xs`) `Global => (In_Out => (...))` aspects (lines 414–425), were
misread as reads of the outer, not-yet-initialized objects — even though a
`Global` aspect is a contract, never executable code at that textual
position, and the objects are correctly initialized by plain `:=`
assignments later in the enclosing body (`sparknacl-core.adb:512–552`).
GNATprove proves the whole corpus; this pattern had zero support from the
oracle.

Root cause and fix are recorded in full as `FP-039` in
`quality/known_analysis_issues.tsv`: `Finalize_Node`'s whole-body,
post-convergence walk in `flow_interp.adb` only excluded recursion into a
foreign `Ada_Subp_Body` (the `FP-017` fix, for an unrelated bug), not into
an `Ada_Aspect_Spec`, so it walked straight into a nested subprogram
*declaration*'s `Global` aspect text and classified each named identifier as
an ordinary read. Fixed by returning immediately from `Finalize_Node` on
`Ada_Aspect_Spec`, before the generic recursion. Regression fixtures:
`tests/verification_global_aspect_reference_clean.adb` (the exact SPARKNaCl
shape) and `_guard.adb` (a genuine uninitialized read nearby, confirming the
fix doesn't blunt real detection), both run by `run_verification.sh`.

Before/after on this corpus:

| | `Definite_Error` | `Proved_Safe` | Total obligations |
| --- | ---: | ---: | ---: |
| Before `FP-039` | 48 | 3,454 | 9,646 |
| After `FP-039` | 0 | 3,457 | 9,531 |

`FP-039` is closed.

## Interpretation

This is the first benchmark in this project where GNATprove could actually
run project-wide (unlike `benchmarks/aws/`, which never got past project
preprocessing) and where the two tools' obligations overlap densely enough
for a real per-check comparison, not just an aggregate pass/fail. On the 886
obligations both tools could independently evaluate at the same location,
AdaLang never disagreed with GNATprove's oracle in either risky direction:
no false "safe," no false "error." The one real precision bug this run
surfaced (`FP-039`) was in a part of the analysis this benchmark was not
specifically targeting — aspect-specification handling, not scalar
arithmetic — which is itself a useful data point: independent-oracle
validation against a real, fully-proved corpus finds bugs a synthetic
fixture corpus would not think to construct.

What this does not establish: AdaLang's `Unsupported`/`Unproved` share of
this corpus (63% of all obligations) is large, and the "AdaLang conservative"
bucket (850 of 886 matched pairs) confirms AdaLang is answering "I don't
know" far more often than GNATprove does — expected, given the documented
narrower and non-relational domain, but a reminder that "0 false positives"
here is a precision result, not a recall one. Closing the two "next steps"
bullets in `quality/README.md` (independent-oracle comparison, project-scale
real-code corpus) should be considered a first data point, not a final
number — future SPARKNaCl re-runs (new revisions, or after other precision
fixes) should be added here to build a trend rather than a single snapshot.
