## Setup note: a `sparklib.gpr` resolution order that no longer held

`README.md`'s documented approach — putting `COAP_SPARK_SPARKLIB` ahead of
`coap_spark_root` on `GPR_PROJECT_PATH` so `with "sparklib.gpr";` resolves
to the standalone FSF-16 crate instead of the pinned checkout's own
`sparklib.gpr` wrapper — did not hold on this run's toolchain: both
`adalang_analyzer` and `gnatprove` kept resolving to the checkout's own
`sparklib.gpr` regardless of `GPR_PROJECT_PATH` ordering, failing with
`sparklib_external.gpr not found` (or, if Alire's own workspace path leaked
in first, the wrong 14.1.1-era copy). Worked around by temporarily moving
the pinned checkout's own `sparklib.gpr` aside — a file inside the
disposable `/private/tmp` clone, never a file in this repository — so
`with "sparklib.gpr";` had only the standalone FSF-16 crate left to
resolve to; confirmed correct by matching the crate's own `Object_Dir`/
`Library_Dir` against the `sparklib_lib`/`sparklib_obj` directories
`run.sh` itself creates. Filed here rather than as a `README.md` rewrite
since it wasn't independently re-confirmed as a permanent toolchain
regression (vs. e.g. a leftover Alire cache on this run's host) — worth
watching on the next re-run.

## Why the new `/`, `mod`, `rem` SMT support didn't move this corpus

The standalone AdaLang `proofSummary` shows a small drop versus baseline —
11,939 obligations (was 11,949, −10), 1,477 `Proved_Safe` (was 1,484, −7),
3,992 `Unsupported` (was 3,995, −3) — but `Unproved` is **byte-identical**
(6,403 = 6,403). Since nothing moved out of `Unproved` into `Proved_Safe`,
this small delta is confined to the unmatched/coverage-only pool (plausibly
the same class of run-to-run obligation-count noise `RESULTS_2026-08-08.md`
already documents for GNATprove's own message counts, e.g. its 7,683 vs.
this run's identical 7,683), not a division/modulo/remainder effect.

Read against `benchmarks/coap_spark/README.md`'s own account of what's
actually stuck here (`Fits_Into` preconditions, `rflx_rflx_arithmetic`),
this is not surprising in hindsight: `FP-047`'s fix targeted `/`, `mod`, and
`rem`, deliberately leaving exponentiation (`**`) out of scope — no bounded
case-split precedent existed anywhere in the codebase to build one on. But
`RFLX_Types.Fits_Into`'s own precondition is shaped like `Value < 2 ** Size`
— **exponentiation**, the one operator this fix explicitly did not cover —
so it was never going to move regardless of how correct the `/`/`mod`/`rem`
translation is. `rflx_rflx_arithmetic`'s division/multiplication-heavy
conversions were the more plausible candidate for this fix to help, but
apparently either don't hit the exact shape `FP-047`'s conservative
"provably nonzero divisor" guard accepts (a literal or a simple identifier
with a known flow range — RecordFlux-generated divisors are more plausibly
compound expressions, e.g. derived from a buffer size or bit-width formal,
which the guard correctly refuses rather than risk an unsound proof), or
don't appear inside a `Pre`/`Post`/`pragma Assert` condition this fix's two
call sites (`Check_Call_Precondition`, `Check_Proof_Pragma_Assertion`)
actually reach.

**Net assessment:** the fix is safe (zero unsoundness, zero false
positives, unchanged) and it is real, general capability, confirmed
independently on the `tests/verification_vc_division*.adb` regression
fixtures — it simply doesn't reach this specific corpus's stuck shape. A
bounded-exponentiation case-split (explicitly out of scope for `FP-047`)
is the more promising next step for `Fits_Into` specifically, if this
corpus's proof rate is worth returning to.
