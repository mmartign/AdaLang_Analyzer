## Delta analysis

### The loop-variant fix (`a6239c1`): no measurable movement in this corpus

coap_spark has exactly **one** `Loop_Variant` pragma in its 85 analyzed
files: `pragma Loop_Variant (Increases => Segment_Last);` at
`rflx-coap_client-session_environment.adb:90`, inside
`Split_String_In_Repeatable_Options`'s segmenting loop. Its AdaLang status
is **still `Unproved`**, unchanged from before today's fix.

This is not a gap in the fix — it is `a6239c1`'s own gating working as
designed. `Mark_Variant_Progress` in `flow_interp.adb` only calls the new
`Decide_Variant_Progress` SMT query when
`Invariants_Usable_For_Variant (Header)` holds, which requires **every**
leading `Loop_Invariant` at that loop header to already be
`VC_Discharged` for both initialization and preservation. This loop
carries five leading invariants, including:

```ada
pragma Loop_Invariant
   (CoAP_SPARK.Options.Lists.Length (Option_List) =
    CoAP_SPARK.Options.Lists.Length (Option_List'Loop_Entry) +
    CoAP_SPARK.Options.Lists.Capacity_Range (Order_Index));
```

an equality over a formal container's `Length`/`Capacity_Range` — outside
AdaLang's bounded-scalar verification subset, so this invariant's own
preservation cannot be `VC_Discharged`. `Invariants_Usable_For_Variant`
therefore returns `False` for this header, `Decide_Variant_Progress` is
never invoked, and the obligation falls back to the same
"not discharged" outcome it always had. **Bucket doesn't move, and this is
a clean, verifiable reason why** — not a defect in the fix, just a corpus
with zero loop variants shaped to exercise it (its one candidate is gated
by an unrelated, pre-existing container-arithmetic limitation).

### An unplanned finding: four new `Definite_Error` candidates, likely false positives

`Definite_Error` went from 0 (inferred from `RESULTS_2026-08-11.md`'s own
arithmetic: `1,760 + 7,037 + 3,530 + 67 = 12,394`, leaving no room for any)
to 4 today. All four are `integer-overflow` on the identical shape —
`Buffer'First - 2` inside `Buffer'First .. Buffer'First - 2 + Types.Index
(Size + 1)` — in `coap_spark-client_session.adb:41` and `:44`, and
`coap_spark-server_session.adb:43` and `:46`. `Types.Index` is
`RFLX_Types.Index`, generated by RecordFlux as `type Index is new Length
range 1 .. Length'Last;` (`Length is new Natural`); its true Ada base
range inherits from `Length`'s (ultimately `Natural`'s/`Integer`'s) full
signed base, comfortably including `Buffer'First - 2 = 1 - 2 = -1`.

GNATprove proves the overflow check safe at all four exact locations
(`coap_spark-client_session.adb:41:72: info: overflow check proved`, and
the matching three), and its own per-subprogram summary in
`gnatprove.out` shows `CoAP_SPARK.Client_Session.Read ... proved (10
checks)` — the whole subprogram, no residual. These did **not** land in
Bucket 4 ("AdaLang false positive") of the matched-pair comparison,
because `compare.awk` requires an exact 1:1 obligation count per
`(file, line, kind)`: AdaLang emits **three** separate `integer-overflow`
obligations per line (the `Buffer'First - 2` sub-expression, the full
`Buffer'First - 2 + Types.Index (Size + 1)` expression, and `Size + 1`)
against GNATprove's **one** `overflow check` message per line, so all four
fall into "count-mismatch keys ... needs manual review" instead — manual
review here (cross-checking `gnatprove-prove.oneline` and
`gnatprove.out` directly, as above) resolves that review in favor of false
positive.

Git blame rules out either named commit as the cause at the code level:
`Known_Arithmetic_Overflow` and `Definitely_Outside_Range` in
`flow_interp.adb` — the functions that decide `Definite_Error` for
overflow checks — are unchanged since commit `453270f8` (2026-07-22),
weeks before today's session; neither `a6239c1` nor `f8a0375` touches
either function (`git show <commit> -- flow_interp.adb | grep -c
Known_Arithmetic_Overflow` is 0 for both). The decision logic itself is
old and was already capable of this false positive on a derived subtype
shaped like `Types.Index`. What changed is exposure: `Unreachable` dropped
by exactly 2 this run, and `a6239c1`'s own diff adds 276 lines to
`flow_interp.adb`'s CFG/before-after state tracking (needed for
`Prove_Loop_Preservation_VCs`'s new variant-progress pass) — a plausible,
though not conclusively proven, mechanism for previously-unreached
overflow checks on this exact node shape to now be evaluated at all. This
is offered as the best-supported hypothesis available from one
before/after snapshot, not a proven root cause.

**This is worth surfacing on its own merits**, independent of which commit
caused it: it is a real, newly-observable candidate false positive on a
RecordFlux-generated derived integer type, confirmed against GNATprove's
own proof of the same four locations, and it sits in a part of the
comparison (`compare.awk`'s count-mismatch pool) that is not
auto-classified into the risk buckets the headline table reports — a
reminder that "0 in Bucket 3/4" does not mean zero risk when the
count-mismatch pool is 813 entries deep and mostly unaudited.

## Follow-up fix, same day: `Overflow_Base_Range` (FP-049)

Root-caused and fixed the four `Definite_Error` obligations above.
`Known_Arithmetic_Overflow` and `Check_Integer_Overflow`'s external-prover
branch resolved an arithmetic operation's base range via a single
`P_Base_Type` hop to the *immediate* parent type, then read that parent's
own visible `P_Discrete_Range` — for `RFLX_Types.Index` (`type Index is
new Length range 1 .. Length'Last;`, itself `type Length is new
Natural;`), that one hop lands on `Length`, whose own visible range is
still `Natural`'s narrow `0 .. Natural'Last`, not the true unconstrained
base range every derivation ultimately inherits (`Integer`'s full signed
range). `Buffer'First - 2` (`Buffer'First` = `Index'First` = 1) evaluates
to -1: outside `Length`'s and `Index`'s own declared constraints, but
comfortably inside the real base range GNATprove correctly checks against.

Fixed with a new `Overflow_Base_Range` helper (`src/adalang_analyzer-flow_interp.adb`):
walks to `P_Root_Type` instead of stopping at one `P_Base_Type` hop, but
only when a real derivation parent exists (`P_Base_Type` non-null) — a
first attempt that walked unconditionally regressed differently, since
`P_Root_Type` on Libadalang's own synthetic universal-integer root (the
type of a bare named-number initializer like `2**14`) resolves to a
placeholder `-1 .. 1` range, not "no known range," turning literal number
declarations into new false `Definite_Error`s until this was caught by
re-running the existing `sparknacl` regression suite and traced to source.

Re-verified against the exact same corpus checkout and full obligation
set as the re-run above:

| | Before this fix | After this fix | Δ |
| --- | ---: | ---: | ---: |
| `Definite_Error` | 4 | **0** | **-4** |
| `Proved_Safe` | 1,791 | 1,795 | +4 |

A full before/after diff of every one of the 12,393 proof obligations
(matched by file/line/kind/operation) confirms this is the *entire*
effect: exactly the 4 targeted `Buffer'First - 2` obligations flip from
`definite-error` to `proved-safe` (matching GNATprove's own verdict at
all four locations), 0 obligations gained or lost, and 0 new
`Definite_Error` anywhere else in the corpus. The same diff technique
against `sparknacl`, `saatana`, `libkeccak`, and `tokeneer`'s
already-recorded results from this session shows zero change on all
four — this fix's effect is isolated to the exact multiply-derived-type
shape it targets. Covered going forward by
`tests/verification_vc_derived_overflow_base.adb`; logged as `FP-049` in
`quality/known_analysis_issues.tsv`.

A suspected ~15x wall-clock slowdown on `sparknacl` surfaced while
investigating this fix's cost turned out to be unrelated host contention,
not the fix itself: timing the unmodified pre-fix binary against the
identical corpus in the same session reproduced the identical slowdown.
