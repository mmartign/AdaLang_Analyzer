## Delta analysis

**`Proved_Safe` +90, `Unproved` −91, `Unsupported` −4 — attributable to
`f8a0375` (scalar-sort resolution), not `a6239c1` (loop variant).** The
current run's `Proved_Safe` obligations break down by kind as: `index-check`
90, `initialization-check` 42, `division-by-zero` 12, `range-check` 2.
`f8a0375` replaced a text-heuristic type guess (`Formal_Sort`'s old
type-mark spelling check, and an absence-of-Flow_Domain-range guess for
enums) with real semantic resolution (`Type_Sort`/`Expression_Sort`, via
`P_Canonical_Fully_Qualified_Name`, `P_Is_Int_Type`, `P_Is_Enum_Type`) used
throughout identifier, field-access, boolean-literal, and
formal-parameter-binding translation — the same symbolic-assignment
machinery that underlies index-check, range-check, initialization-check,
and division-by-zero discharge generally, not just enum-typed code. Saatana
is Word_32/Byte-heavy scalar arithmetic with some enum use
(`Old_State_Words`, mode/algorithm-state enumerations), so a broad gain
across exactly these four scalar-bounded kinds — and no gain in
`precondition`/`postcondition`/`assertion` kinds, which don't route through
this code path — is the expected signature of this fix, not the loop-variant
one.

**The loop-variant fix (`a6239c1`) produced a null result on Saatana: all 4
`Loop_Variant` obligations remain `Unsupported`, none reached
`Proved_Safe`.** Saatana's Phelix loops carry multi-clause variants, e.g.
`saatana-crypto-phelix.adb:139`:
```
pragma Loop_Variant (Decreases => Msg_Len,
                     Increases => This.CS.I,
                     Increases => This.CS.Msg_Len,
                     Increases => Src_Idx,
                     Increases => Dst_Idx,
                     Increases => Dst_Nxt);
```
Inspecting `src/adalang_analyzer-flow_interp.adb`'s `Finalize_Loop_Variant`
shows the actual reason: all four sites report `status: unsupported`,
`explanation: "loop-variant progress is outside the bounded verification
subset"` — the *first* check in that procedure (`if not Boundary_Supported
then Record_Unsupported (...)`), a whole-enclosing-subprogram gate (CFG
completeness and the absence of *any* unsupported construct anywhere in the
subprogram body), not the new leading/direction/progress logic `a6239c1`
added. Because each of these four `Loop_Variant` pragmas sits inside one of
Phelix's large word-processing procedures, something else in that same
subprogram body already falls outside the bounded verification subset, so
`Boundary_Supported` is `False` for the whole enclosing subprogram and the
loop-variant obligation is gated off before `Item.Leading` or
`Item.Direction_Supported` is ever consulted. (Separately, Saatana's
variants are 5–6-clause, not the single leading clause the new logic
targets — `Count = 1` is required for `Direction_Supported`; that check
would also fail here, but never gets reached because the boundary gate
fires first.) `loop-variant` also isn't one of `compare.awk`'s
GNATprove-mapped kinds, so this null result doesn't touch the matched-pair
buckets either way. Saatana's dense, hand-optimized single-file cipher
loops are simply not the shape this fix targets — consistent with this
benchmark's recurring lesson (see the 2026-08-11 re-run note in
`RESULTS_2026-08-04.md`) that not every real-code corpus reacts to every
fix.

**New `Definite_Error`: `test_phelix.adb:41`, `S'Length * 2` may overflow —
outside GNATprove's own analysis scope, so it doesn't enter any
matched-pair bucket.** `tests/phelix/test_phelix.adb` is declared
`procedure Test_Phelix with SPARK_Mode => Off`; GNATprove's `--mode=prove`
output has zero messages for this file (confirmed against
`gnatprove-prove.oneline`, whose 51 `test_phelix*` matches are all
`test_phelix_api.adb`, the sibling `SPARK_Mode => On` test driver) — the
file is entirely outside what GNATprove checked, by the corpus's own
design, not a benchmark gap. The obligation itself (`Result : String (1 ..
S'Length * 2)` in the `Image` function) is plausibly a case the old
text-heuristic type guess previously mis-sorted as `Unsupported`
(`Sort_Mismatch`) and `f8a0375`'s real type resolution now evaluates
correctly enough to report a genuine bounded-arithmetic finding. Because
GNATprove made no claim about this file at all, this benchmark cannot
independently confirm or refute it — it is new information from AdaLang
alone, not a "false positive" bucket entry, and the matched-pair split
staying at 0/101/0/0/0 confirms it landed nowhere near the GNATprove-covered
set.

**`Unsupported` −4 traces to the `assertion` kind, not the two headline
fixes directly.** The AdaLang-only (no-GNATprove-mapping) `assertion` count
dropped from 13 to 9, exactly matching the total obligation-count
decrease. The current run additionally reports 4 obligations under a
distinct `loop-variant` kind (all `Unsupported`, see above) that
`compare.awk` doesn't map and so never appeared in either the 2026-08-04 or
this report's coverage tables. The precise old-to-new obligation-identity
mapping isn't independently verifiable without the 2026-08-04 raw JSON
(not retained), so this report states the observed correlation plainly
rather than asserting a specific renaming mechanism as fact.

## Bottom line

Both landed commits show up in this run, in the direction their own commit
messages predict, and neither moves the risk-relevant matched-pair buckets:
`Proved_Safe` nearly tripled (56 → 146) with the gain concentrated in
`index-check`/`initialization-check`/`division-by-zero`/`range-check` — the
scalar-bounded kinds `f8a0375`'s semantic scalar-sort resolution feeds —
while the loop-variant fix (`a6239c1`) produced a clean null result here:
all 4 of Saatana's `Loop_Variant` obligations remain `Unsupported`, gated
off by a whole-subprogram `Boundary_Supported` check before the new
discharge logic is ever reached, on multi-clause variants the fix wasn't
built to target regardless. The matched-pair bucket split is bit-identical
to baseline (0/101/0/0/0): zero possible unsoundness, zero false positives,
even with 90 more `Proved_Safe` calls corpus-wide — none of them happen to
land where GNATprove also reports at the same location, the same
sample-size caveat the baseline already raised for the original 56. The one
new `Definite_Error` (`test_phelix.adb:41`) sits in `SPARK_Mode => Off` test
code GNATprove never analyzes, so it is new information from AdaLang alone,
not a benchmark disagreement — it neither confirms nor contradicts the
oracle. Saatana remains a small, third-party, independently-authored
corroborating data point: real movement, correctly attributed to the
commit that plausibly caused it, with no headline-risk regression.
