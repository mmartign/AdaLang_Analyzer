## GNATprove boundary

Both unmodified GNATprove lanes stopped on the same two source locations:

```text
aws-client-http_utils.adb:759:10: error: prefix of "VALID_VALUE"
  attribute must not have Discard_Names
aws-client-http_utils.adb:761:13: error: prefix of "VALID_VALUE"
  attribute must not have Discard_Names
```

`-k`, `-u`, and `--no-global-generation` did not avoid the project-wide
preprocessing failure. Therefore this run produced no common set on which
AdaLang `Proved_Safe` and GNATprove proof outcomes could honestly be compared.

For diagnostic purposes only, a derived project excluded that one body while
leaving all Ada source unchanged. GNATprove then reached flow analysis in
76.47 seconds with `--no-subprojects`, but the run still ended with SPARK
legality errors and no aggregate flow checks:

- 583 units listed in the detailed report, including required dependency
  units;
- 4,150 declared subprogram/package entities;
- 221 entities reported as analyzed (5.33%);
- 3,871 explicit `SPARK_Mode => Off` skips;
- 75 entities marked not analyzed;
- 65 units with an error while checking `SPARK_Mode`;
- prominent boundaries included controlled/class-wide socket types,
  Templates Parser containers declared with `SPARK_Mode => Off`, and
  discriminated poll sets.

This diagnostic lane is not a proof result and is not directly comparable to
AdaLang's 348-file pass. It quantifies the migration work required before
GNATprove can serve as a proof oracle for AWS.

## Confirmed AdaLang precision problem

Spot checks of AdaLang's `Definite_Error` initialization results included:

- `aws-http2.adb:41`: `E : String renames Exception_Message`; `E` aliases an
  initialized input parameter, but reads of `E` were classified definite
  initialization errors.
- `aws-messages.adb:558`: a default-initialized
  `Ada.Strings.Unbounded.Unbounded_String` passed to an append operation was
  classified as definitely uninitialized.
- `aws-config-ini.adb:140` and `aws-attachments.adb:588`: default-initialized
  `Ada.Text_IO.File_Type`/`Ada.Streams.Stream_IO.File_Type` objects passed to
  `Open` were classified as definitely uninitialized.

These were analyzer false positives, not merely inconclusive results.

## FP-020 post-fix validation

The same pinned 348-file project was rerun after correcting initialization
state seeding and value-read classification. The regression-tested correction:

- propagates the source state for simple object renamings;
- reserves definite-uninitialized state for resolved scalar declarations and
  scalar `out` parameters;
- treats non-scalar/private and address-overlay objects conservatively; and
- does not create value-read obligations for bounds/address/access attributes
  or the base name of an assignment target.

After both initialization precision corrections (`FP-020` and the later
`FP-019` unresolved-call boundary), the fixed `--verify` lane completed in
30.20 seconds with:

| Status | Count | Share |
| --- | ---: | ---: |
| `Proved_Safe` | 5,072 | 21.50% |
| `Definite_Error` | 0 | 0.00% |
| `Unproved` | 8,562 | 36.29% |
| `Unsupported` | 9,961 | 42.22% |

The lane enumerated 23,595 obligations. The lower total reflects removal of
initialization obligations for syntactic uses that do not read an object's
value. The sampled `Unbounded_String` and `File_Type` cases are now `Unproved`,
the simple renaming case no longer produces a definite error, and all 265
baseline definite errors are eliminated. `FP-020` is closed; the deliberately
broken scalar-renaming regression remains `Definite_Error`.

## FP-019 post-fix validation

The initial no-project AWS investigation had one residual open false positive:
`AWS.Net.Acceptors.Get` passed `Error` to `Sets.Is_Read_Ready` as an `out`
actual, but full-batch provider resolution failed and a later read was reported
as definitely preceding every write. The same boundary also affected `Count`
and `Success` in that body.

The fix represents an unresolved simple call actual as a terminal unknown
first access. A call whose formal mode cannot be resolved may initialize the
object, so analysis cannot bypass it and make a definite claim about a later
read. Resolved input, output, and input-output actuals retain their previous
read/write classifications.

Validation covered both AWS invocation shapes:

- the exact original 273-file no-project run: all three
  `aws-net-acceptors.adb` instances disappeared; `Uninitialized_Read` fell
  from 28 to 4 and total findings from 275 to 251;
- the pinned configured 348-file project: `Uninitialized_Read` fell from 19
  to 12 and `--recommended` findings from 437 to 430. No
  `aws-net-acceptors.adb` instance remains.

`FP-019` is closed. Together with `FP-020`, this leaves zero open known false
positives in the release metrics.

## Interprocedural effect-summary validation

After extending the shared call-summary registry with formal read/write,
all-normal-return initialization, and transitive nonlocal-write effects, both
configured 348-file lanes were repeated. Summary discovery used an isolated
Libadalang context so a failed speculative property query could not memoize an
error into the ordinary checking pass.

The `--recommended` lane remained exactly stable at 430 findings, including
all 77 existing `Dead_Store` findings. The bounded-verification lane retained
the same 23,595 obligations and zero `Definite_Error` outcomes, with:

| Status | Before summaries | With summaries | Delta |

| `Proved_Safe` | 5,072 | 5,156 | +84 |
| `Definite_Error` | 0 | 0 | 0 |
| `Unproved` | 8,562 | 8,479 | -83 |

Thus 84 previously inconclusive obligations became proved safe without adding
a definite-error claim or changing ordinary-analysis findings. The remaining
18,439 unproved or unsupported obligations continue to dominate this ordinary
Ada corpus and preserve the documented bounded-verification positioning.

## Interpretation

The experiment supports AdaLang's stated positioning on ordinary Ada: it
obtains broad, quick project coverage and useful readiness information where
GNATprove requires deliberate SPARK boundaries. It does **not** validate
AdaLang's proof accuracy against GNATprove, because unmodified AWS never
reached GNATprove proof generation. The baseline exposed a project-scale
initialization precision defect, which the pinned post-fix rerun confirms is
corrected; that correction does not turn GNATprove's blocked lane into
comparative proof evidence.

The next differential milestone should use an AWS component deliberately
adapted to SPARK, with contracts and non-SPARK dependencies isolated, so both
tools enumerate the same initialization/range/index/overflow obligations.
