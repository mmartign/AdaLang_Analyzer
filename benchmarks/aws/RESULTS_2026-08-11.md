## `--verify`: the false positive `RESULTS_2026-08-09.md` flagged is now gone

| Status | 2026-08-09 | 2026-08-11 | Δ |
| --- | ---: | ---: | ---: |
| `Proved_Safe` | 5,702 | **5,702** | 0 |
| `Definite_Error` | 4 | **0** | **−4** |
| `Unproved` | 10,068 | 10,050 | −18 |
| `Unreachable` | 352 | 352 | 0 |
| `Unsupported` | 13,070 | 13,060 | −10 |
| Total obligations | 29,196 | 29,164 | −32 |

`Proved_Safe` is bit-for-bit identical (5,702), so `FP-047`'s new `/`,
`mod`, `rem` SMT support produced **zero net movement** on this corpus —
AWS apparently has no bound-checkable division/modulo/remainder expression
that flips from unsupported/unproved to proved-safe under it. All four
`Definite_Error` outcomes, though, are gone. These are exactly the
`aws-server-push.adb` protected-body writes `RESULTS_2026-08-09.md`
documented in full (`Shutdown_If_Empty.Open := Object.Open;`, `Info.Size
:= ...`, and its three siblings) — the own-name-qualified `out`-parameter
shape that flagged them as "uninitialized on every incoming path" is
exactly what `FP-046` (closed in this repository's `flow_interp.adb`
between the two runs; see `quality/known_analysis_issues.tsv`) fixed. The
remaining −18 `Unproved`/−10 `Unsupported` movement (net −32 total,
alongside the −4 `Definite_Error`) is consistent with the same fix
changing how those four writes' surrounding obligations get registered,
not a new false positive or a regression.
